## How to enable different document edit modes?

WordProcessing module of <a href="https://products.groupdocs.com/editor/net" target="_blank" rel="nofollow noopener noreferrer">**GroupDocs.Editor**</a>, that is responsible for converting all WordProcessing formats to <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor/editabledocument" target="_blank" rel="nofollow noopener noreferrer">EditableDocument</a> instances and backward (from <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor/editabledocument" target="_blank" rel="nofollow noopener noreferrer">EditableDocument</a> to some of WordProcessing format), contains two modes: *float* and *paginal* (also known as *paged*), where first one - float, is default. These modes are presented by two properties with the same name and type:

```csharp
public bool EnablePagination {get; set;}
```

At first, such property is present in the <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor.options/wordprocessingeditoptions" target="_blank" rel="nofollow noopener noreferrer">`WordProcessingEditOptions`</a> class and is doubled in the <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor.options/wordprocessingeditoptions/wordprocessingeditoptions/#constructor" target="_blank" rel="nofollow noopener noreferrer">overload of class constructor</a>, which obtains one boolean parameter of the same name. In this case this option is responsible for selected mode during forward (WordProcessing to <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor/editabledocument" target="_blank" rel="nofollow noopener noreferrer">EditableDocument</a>) conversion.

Secondly, such property is present in the <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor.options/wordprocessingsaveoptions" target="_blank" rel="nofollow noopener noreferrer">WordProcessingSaveOptions</a> class and is responsible for selected mode during backward (<a href="https://reference.groupdocs.com/editor/net/groupdocs.editor/editabledocument" target="_blank" rel="nofollow noopener noreferrer">EditableDocument</a> to WordProcessing) conversion.

Main "rule of thumb" for the end-user is to preserve the same mode during full document roundtrip and do not change it. In other words, if input document was converted to the <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor/editabledocument" target="_blank" rel="nofollow noopener noreferrer">EditableDocument</a> (followed by the HTML emitting from <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor/editabledocument" target="_blank" rel="nofollow noopener noreferrer">EditableDocument</a> instance) in the *float* mode, then the resultant <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor/editabledocument" target="_blank" rel="nofollow noopener noreferrer">EditableDocument</a> instance (obtained from document, edited on client-side) should be converted back to the WordProcessing format also in the *float* mode (same rule for *paginal* mode too).

Main distinguish of these two modes lies in the form of representation of the input WordProcessing document. By default all WordProcessing formats internally have no pages and page division, they are internally represented as a float smoothness and pageless structure. However, they contain page-related information like headers, footers, page watermarks, page numbering formatting info etc. And when WordProcessing document is opened in some of desktop or browser-based text processor like MS Word, OpenOffice or Google Docs, this text processor dynamically and "on the fly" splits the document onto multiple pages, which are re-calculated every time when user is performing some edits in document content. For example, when user removes the line from the beginning of the huge document, the empty space is "collapsing", and all subsequent content is like "moving upward' to fill the gap, where removed line was located. Same real-time calculations are valid also for situations when content is added, - new inserted content is pushing the existing content to move downward, with creating new pages if necessary.

The problem is the most of used client-side browser-based JavaScript HTML WYSIWYG editors like TinyMCE or CKEditor do not support pages, page separation and described calculations at all. They support only documents with pageless structure. That's why GroupDocs.Editor support two modes:

* In the *float* mode the WordProcessing document in represented in pageless form. Content is not separated on pages, There are no any page-related entities like headers, footers, watermarks and page numbers. This mode is the most suitable for almost all widespread WYSIWYG HTML-editors and that's why this mode is default.
* In the *paginal* mode the WordProcessing document in represented as a set of pages, where content is divided onto pages in the same way as MS Word does. Al page-related entities like headers, footers, watermarks and page numbers are present. This mode should be turned on manually (as it is described above) and is fitting for scenarios where end-user is able to process such content in some appropriate and suitable way, for example, in his own-made HTML editing software.

## Paginal edit mode in PDF

Along with family of WordProcessing formats, GroupDocs.Editor support a PDF as one of output (resultant) formats. In other words, input WordProcessing may be opened, edited, but saved not only to the WordProcessing, but also to the PDF. Prior GroupDocs.Editor version 20.3 the *paginal* mode was accessed only for forward and backward WordProcessing conversions, and was not available for PDF. This means that there was no possibility to generate an output PDF in *paged* mode, regardless of <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor.options/wordprocessingeditoptions/enablepagination" target="_blank" rel="nofollow noopener noreferrer">EnablePagination</a> flag in the <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor.options/wordprocessingeditoptions" target="_blank" rel="nofollow noopener noreferrer">WordProcessingEditOptions</a> class. In other words, even if input WordProcessing document was converted to <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor/editabledocument" target="_blank" rel="nofollow noopener noreferrer">EditableDocument</a> in *paginal* mode, the output PDF will be generated in *float* mode.

Starting from GroupDocs.Editor version 20.4 these two conversion mode were added into the PDF processor. Now <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor.options/pdfsaveoptions" target="_blank" rel="nofollow noopener noreferrer">PdfSaveOptions</a> class contains the same property - <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor.options/pdfsaveoptions/enablepagination" target="_blank" rel="nofollow noopener noreferrer">EnablePagination</a> boolean flag, which, like the same in WordProcessing, has `false` default value, which means *float* mode, when `true` value means *paginal* mode. If input WordProcessing document was converted to <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor/editabledocument" target="_blank" rel="nofollow noopener noreferrer">EditableDocument</a> in *paginal* mode, the output PDF should be generated in *paginal* mode too, with enabled <a href="https://reference.groupdocs.com/editor/net/groupdocs.editor.options/pdfsaveoptions/enablepagination" target="_blank" rel="nofollow noopener noreferrer">EnablePagination</a> flag.
