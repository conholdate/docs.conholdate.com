## Por qué usar Alpine Linux en Docker

- **Tamaño reducido**: Las imágenes de Alpine son aproximadamente 5 MB, comparado con cientos de MB en distribuciones completas.
- **Seguridad mejorada**: Menos paquetes instalados significa una superficie de ataque más pequeña.
- **Velocidad de inicio**: Las imágenes ligeras se descargan y arrancan más rápido.

## Estructura básica de un Dockerfile para Alpine

```dockerfile
# Usar una imagen base de Alpine
FROM alpine:latest

# Instalar dependencias necesarias para la compilación
RUN apk add --no-cache build-dependencies

# Copiar el código fuente
COPY . /app
WORKDIR /app

# Compilar la aplicación
RUN make

# Opcional: crear una imagen final más pequeña usando multi-stage build
FROM alpine:latest
COPY --from=0 /app/myapp /usr/local/bin/myapp
CMD [\"myapp\"]
```

## Instalación de dependencias de compilación

Alpine usa `apk` como su gestor de paquetes. Para instalar herramientas de compilación:

```bash
# Instalar herramientas básicas de compilación
RUN apk add --no-cache \\
    build-base \\
    musl-dev \\
    linux-headers \\
    git \\
    make \\
    gcc \\
    g++
```

- `build-base`: metapaquete que incluye gcc, g++, make, libc-dev, etc.
- `musl-dev`: cabeceras para musl libc (necesario para compilar C/C++)
- `linux-headers`: cabeceras del kernel de Linux

## Ejemplos de compilación para diferentes lenguajes

### C/C++

```dockerfile
FROM alpine:latest AS builder
RUN apk add --no-cache build-base
COPY . /app
WORKDIR /app
RUN make

FROM alpine:latest
RUN apk add --no-cache libc6-compat
COPY --from=builder /app/myapp /usr/local/bin/myapp
CMD [\"myapp\"]
```

> Nota: Alpine usa `musl libc`, mientras que la mayoría de software C/C++ se compila contra `glibc`. Para mayor compatibilidad, instala `libc6-compat` en la imagen final.

### Go

```dockerfile
FROM golang:1.21-alpine AS builder
RUN apk add --no-cache git
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -a -installsuffix cgo -o myapp .

FROM alpine:latest
RUN apk add --no-cache ca-certificates
COPY --from=builder /app/myapp /usr/local/bin/myapp
CMD [\"myapp\"]
```

> Nota: `CGO_ENABLED=0` deshabilita CGO, creando un binario estático que no depende de `musl`.

### Node.js

```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
CMD [\"node\", \"dist/index.js\"]
```

### Python

```dockerfile
FROM python:3.11-alpine AS builder
RUN apk add --no-cache build-base
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN pip install --no-cache-dir .

FROM python:3.11-alpine
WORKDIR /app
COPY --from=builder /usr/local/lib/python3.11/site-packages /usr/local/lib/python3.11/site-packages
COPY --from=builder /app /app
CMD [\"python\", \"main.py\"]
```

### Rust

```dockerfile
FROM rust:1.74-alpine AS builder
RUN apk add --no-cache musl-dev
WORKDIR /app
COPY Cargo.toml Cargo.lock ./
RUN cargo fetch
COPY . .
RUN cargo build --release

FROM alpine:latest
RUN apk add --no-cache libc6-compat
COPY --from=builder /app/target/release/myapp /usr/local/bin/myapp
CMD [\"myapp\"]
```

## Consejos para imágenes finales más pequeñas

1. **Usa multi-stage builds**: Compila en una imagen con herramientas de compilación y copia solo el binario final a una imagen ligera.
2. **Elimina dependencias innecesarias**: Usa `--no-cache` con `apk add` y limpia el caché con `rm -rf /var/cache/apk/*`.
3. **Usa imágenes oficiales**: Las imágenes oficiales suelen estar optimizadas.
4. **Evita herramientas de desarrollo en producción**: No instales `gcc`, `make`, etc. en la imagen final.

## Resolución de problemas comunes

### Error: `error: can't find the -lstdc++ library`

Solución: Instala `libstdc++` o usa `build-base` que lo incluye.

```dockerfile
RUN apk add --no-cache libstdc++
```

### Error: `error while loading shared libraries: libssl.so.1.1: cannot open shared object file`

Solución: Instala la biblioteca correspondiente (por ejemplo, `libssl1.1` o `openssl`).

```dockerfile
RUN apk add --no-cache openssl
```

### Error: `sh: make: not found`

Solución: Instala `make` y `build-base`.

```dockerfile
RUN apk add --no-cache build-base
```

### Error: `error: command 'gcc' failed with exit status 1`

Solución: Asegúrate de tener instalado `build-base` y `musl-dev`.

```dockerfile
RUN apk add --no-cache build-base musl-dev linux-headers
```

### Error: `No such file or directory` al ejecutar binarios estáticos

Solución: Alpine usa `musl`, pero algunos binarios están compilados contra `glibc`. Usa `libc6-compat` o compila con CGO deshabilitado (si es posible).

```dockerfile
RUN apk add --no-cache libc6-compat
```"

## Compilar proyecto de API web con GroupDocs.Conversion en Docker {#build-web-api-project-with-groupdocs-conversion-in-docker}

Para compilar una API web que utilice GroupDocs.Conversion para .NET en un contenedor Docker con Alpine Linux, utilice el siguiente archivo Docker de ejemplo:

```docker
FROM mcr.microsoft.com/dotnet/aspnet:6.0-alpine AS base
WORKDIR /app
EXPOSE 80
ENV DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=false

RUN apk add --no-cache icu-libs krb5-libs libgcc libintl libssl1.1 libstdc++ zlib
RUN apk add --no-cache ffmpeg libgdiplus

RUN apk add --no-cache msttcorefonts-installer fontconfig
RUN update-ms-fonts && fc-cache fc-cache -f

FROM mcr.microsoft.com/dotnet/sdk:6.0-alpine AS build
WORKDIR /src
COPY ["YourApi/YourApi.csproj", "TestApi/"]
RUN dotnet restore "YourApi/YourApi.csproj"
COPY . .
WORKDIR "/src/YourApi"
RUN dotnet build "YourApi.csproj" -c Release -o /app/build

FROM build AS publish
RUN dotnet publish "YourApi.csproj" -c Release -o /app/publish

FROM base AS final
WORKDIR /app
COPY --from=publish /app/publish .
ENTRYPOINT ["dotnet", "YourApi.dll"]
```

Como puedes ver, el proceso es el mismo que al construir un proyecto de API web normal en Docker. La principal diferencia radica en la instalación de las bibliotecas necesarias, lo que permite que GroupDocs.Conversion para .NET funcione correctamente en un contenedor Docker:

```docker
ENV DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=false

RUN apk add --no-cache icu-libs krb5-libs libgcc libintl libssl1.1 libstdc++ zlib
RUN apk add --no-cache ffmpeg libgdiplus

RUN apk add --no-cache msttcorefonts-installer fontconfig
RUN update-ms-fonts && fc-cache fc-cache -f
```

Tampoco olvide agregar el archivo `runtimeconfig.template.json` junto al archivo de su proyecto con el siguiente contenido:

```json
{
    "configProperties": {
        "System.Drawing.EnableUnixSupport": true
    }
}
```

Esto evitará la excepción «El inicializador de tipo para `gdip` lanza una excepción". Para obtener más información sobre esto <a href="https://docs.microsoft.com/en-us/dotnet/core/compatibility/core-libraries/6.0/system-drawing-common-windows-only" target="_blank" rel="nofollow noopener noreferrer">leer aquí</a>.
